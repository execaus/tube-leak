# tube-leak

Кросс-платформенное десктопное приложение для скачивания видео с YouTube.

**Статус: greenfield.** Кода пока нет — файл описывает целевую архитектуру и соглашения. По мере появления кода уточняй разделы «Структура» и «Команды» фактическим состоянием репозитория, а не планами.

## Стек

| Слой | Технология |
|---|---|
| Ядро / бэкенд | Rust, Tauri 2 |
| UI | Vue 3 (Composition API, `<script setup>`), Vite, Pinia, TypeScript |
| Скачивание | `yt-dlp` (внешний бинарник, sidecar) |
| Постобработка | `ffmpeg` (внешний бинарник, sidecar) |

Целевые платформы: **Windows, macOS (в т.ч. Apple Silicon), Linux**. Мобильных и веб-версий нет.

Tauri рендерит UI в системном WebView (WebView2 / WKWebView / WebKitGTK). Vue выбран не ради веб-версии, а как слой управления реактивным состоянием очереди и прогресса.

## Архитектурные решения

**yt-dlp и ffmpeg — внешние бинарники, не библиотеки.** Свою реализацию парсинга YouTube не пишем: формат отдачи меняется постоянно, yt-dlp обновляется быстрее любого нашего кода. Бинарники поставляются как Tauri sidecar в `src-tauri/binaries/` с суффиксом целевой тройки (`yt-dlp-x86_64-apple-darwin` и т.п.).

**Вся тяжёлая работа — в Rust.** Фронтенд не запускает процессы и не трогает файловую систему напрямую. Взаимодействие: `invoke` для команд, события Tauri для прогресса.

**Прогресс — через события, не через polling.** yt-dlp пишет прогресс в stdout; парсим его в Rust и эмитим событие на каждое задание (`download://progress` с id задачи). Фронтенд слушает и обновляет Pinia-стор. Никаких таймеров, опрашивающих бэкенд.

**Очередь — источник истины в Rust.** Состояние задачи (`Queued | Fetching | Downloading | Merging | Done | Failed | Cancelled`) живёт в менеджере очереди и переживает перезапуск UI. Стор на фронтенде — проекция, а не хозяин данных.

**Отмена обязательна на каждом этапе.** Долгие операции (скачивание, merge) должны корректно убивать дочерний процесс и подчищать частичные файлы.

**Хранилище раздельное.** История загрузок — SQLite (`rusqlite`, bundled) с версионированными миграциями: она растёт, по ней нужны поиск и сортировка, а запись должна быть атомарной. Настройки — отдельный JSON с записью через временный файл и переименование. Схема и миграции заводятся до первой реализации, которая в них пишет.

**Ошибки типизированные, не строки.** Отдельно выделяются «требуется вход», «нет сети», «недоступно в регионе», «yt-dlp устарел»: пользователь должен понимать, что делать, а не читать stderr.

**Пути и имена файлов санитизируются в Rust.** Заголовки роликов содержат символы, недопустимые в путях Windows, и потенциально `../`. Ни один компонент пути не строится из непроверенного ввода.

## Долговечность и естественное поведение

Требование владельца: программа должна работать как можно дольше и вести себя как обычный пользователь. Отсюда инварианты, которые не пересматриваются по ходу задач:

- Официальный YouTube Data API не используется — yt-dlp обращается к тем же эндпоинтам, что и веб-плеер.
- Собственный парсер выдачи не пишется никогда. Любой свой код отстанет от изменений на стороне YouTube; yt-dlp реагирует на них за дни.
- Соединение прямое, с машины пользователя, без промежуточных серверов. Системные настройки прокси уважаются.
- Число соединений дефолтное. Агрессивное распараллеливание отличает загрузчик от человека и провоцирует ограничения.
- Главный инструмент долгой жизни — обновляемый yt-dlp отдельным контуром (см. ниже).

## Два независимых контура обновления

Их нельзя смешивать: у них разная частота, разный риск и разный механизм.

**1. yt-dlp — часто, без релиза приложения.** YouTube ломает извлечение регулярно, и вшитый в релиз бинарник устаревает за недели. Приложение обновляет yt-dlp самостоятельно, отдельно от собственной версии; иначе каждая поломка на стороне YouTube требует выпуска нового релиза.

**2. Само приложение — плагин `updater` Tauri 2, редко и с подписью.** Приложение периодически проверяет манифест в GitHub Releases, сравнивает версии, скачивает и устанавливает апдейт. Следствия, обязательные к соблюдению в релизном процессе:

- Подпись обязательна: minisign-пара (`tauri signer generate`), публичный ключ — в `tauri.conf.json`, приватный — в секретах CI (`TAURI_SIGNING_PRIVATE_KEY`). Неподписанный апдейт не установится — это защита от подмены артефакта.
- **Linux-релизы выпускаются как AppImage**: плагин обновляет только его, `.deb`/`.rpm` обновляются системным пакетным менеджером.
- Проверка обновлений — не при каждом старте в блокирующем режиме; пользователь должен иметь возможность её отключить.

**Открытый вопрос: откуда раздавать релизы.** Репозиторий приватный, а релизные ассеты приватного репозитория не скачиваются без токена — вшить токен в приложение нельзя, он утечёт из бинарника вместе с доступом к исходникам. Значит, к моменту первого публичного релиза нужно решение: отдельный публичный репозиторий только под релизы, собственный эндпоинт обновлений, либо открытие основного репозитория. Пока приложение не раздаётся наружу, вопрос не блокирует работу.

Автообновление реализуется отдельным эпиком **после MVP**; до тех пор релизный процесс уже обязан соблюдать требования выше (AppImage, подпись в CI) — иначе первый же выпущенный релиз не сможет обновиться.

## Конвенции

- Rust: ошибки — `thiserror` в домейне, конвертация в сериализуемый тип на границе `#[tauri::command]`. `unwrap()` в продакшен-путях недопустим.
- Vue: только Composition API и `<script setup>`. Один стор Pinia на домен, без общего «god store».
- Типы, пересекающие границу Rust↔TS, объявляются один раз в Rust и генерируются/зеркалятся в `src/types/` — расхождение типов ловится на сборке, а не в рантайме.
- Каждый новый формат/качество/постпроцессинг покрывается тестом на уровне `downloader`/`ffmpeg` с фикстурой вывода yt-dlp, без сетевых вызовов в тестах.

## Ресурсы машины

Тестовых контейнеров в проекте нет, но полная сборка Tauri (`npm run tauri build`, холодный `cargo build`) грузит машину сопоставимо: в каждый момент её ведёт **один** агент во всём проекте. Исполнители областей проверяют свою работу быстрыми командами (`cargo test`, `cargo clippy`, `npm run type-check`), полную сборку инициирует ведущий разработки.

## Границы продукта

Приложение — GUI-обёртка над yt-dlp. Обход платных подписок, DRM и региональных ограничений в задачи проекта не входит и не реализуется. Ответственность за соблюдение условий сервиса и авторских прав при скачивании конкретного ролика лежит на пользователе — это стоит отразить в UI при первом запуске.

Но на запуске у владельца служебный экран показал «не отвечает» по обоим инструментам. Заведены два дефекта.

**TL-11 (#12) — ffmpeg в дистрибутиве под Intel, не arm64.** Источник evermeet.cx публикует только x86_64; на Apple Silicon идёт через Rosetta, macOS показывает уведомление про Intel-компонент, `-version` 8.8–11 с при таймауте 5 с. Нужен arm64/universal источник с сохранением Р-3 (GPL-сборка + текст лицензии и ссылка на исходники вложенной версии).

**TL-12 (#13) — yt-dlp стартует 34–39 с при таймауте 8 с.** Не зависит от носителя, прогрева кеша и подписи. CPU 2% — процесс ждёт; стек `__wait4` в загрузчике PyInstaller; сети нет; карантина нет. Таймауты 8 с / 5 с задавались дизайном как стартовая точка «подлежит калибровке по К-4» — калибровка не выполнена, а замеры из отчёта TL-9 (≈8.7 с) не воспроизводятся.

Подтверждено вживую: TL-10 работает — после выхода из приложения осиротевших процессов не остаётся.

**Корневой вывод для будущих задач.** Оба дефекта существуют только на собранном bundle и невидимы в dev-режиме. Проверять приёмочные критерии на `npm run tauri dev` недостаточно: нужен `npm run tauri build`, монтирование `.dmg` и запуск `.app`.
